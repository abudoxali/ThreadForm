## Completed work

**`packages/garment-runtime` (new)** — no React, no Three.js. `garmentManifestSchema` (zod) validates a manifest fetched from `/garments/<id>/manifest.json` at the same untrusted-until-validated boundary as a persisted `Project`; every enum is pinned to its `@threadform/types` union with `satisfies readonly X[]`. `GARMENT_CATALOG` lists garments with a real, loadable manifest (today: one). `CAMERA_PRESETS` defines the six preset framing angles. `resolveGarmentReference` maps a `Project.garment` to a real garment — including M01's pre-manifest placeholder shape (`{garmentId: category, garmentVersion: '0.0.0', category}`), matched **only** on an exact category match, never an unrelated one. 11 tests.

**`packages/3d-engine` (new)** — React Three Fiber rendering. `StudioGarmentCanvas` (Canvas + isolated error boundary + Suspense loading state), `GarmentModel` (GLB load via drei's `useGLTF`, clones the scene graph and every mesh's material so color changes and disposal never touch drei's shared cache), `CameraRig` (OrbitControls + preset framing), `StudioLighting` (3-point rig), `frameGarment` (pure bounding-sphere + aspect-ratio framing math, unit-tested without a GPU). 8 tests.

**First original garment: ThreadForm Essential Tee** — procedurally generated by `scripts/generate-essential-tee.mjs` (hand-authored 2D silhouette extruded for the torso, cylinder sleeves), verified by `scripts/verify-essential-tee.mjs`. 3 meshes, 336 triangles, 31.5 KB GLB, normals + UVs present, honestly labeled `readiness: "development"`. Full provenance in `assets/garments/threadform-essential-tee/PROVENANCE.md`: original, not derived from any third-party asset, with documented known limitations (see below). Source of truth in `assets/garments/`, served copy in `apps/web/public/garments/` (byte-identical, verified).

**Studio wiring** — `GarmentPicker` now shows the real catalog (enabled) plus other categories as honestly disabled ("coming in a later milestone"). Choosing a garment loads and validates its manifest, then creates a real `Project` referencing it. `useResolvedGarment` (new hook) is the only place a `Project.garment` is resolved against `garment-runtime`. `Inspector` exposes real garment-color swatches and camera-preset buttons, both writing through `Project` state (never mutating the manifest). `StudioShell` renders `3d-engine`'s canvas, loaded via `next/dynamic({ssr:false})` so three.js/drei never ship to the picker/recents start screen or run during SSR.

**Domain mutation moved into `project-engine`** — `setGarmentColor`/`setCameraPreset` (`packages/project-engine/src/garment.ts`, 4 tests) are the first two garment-related mutators there, following the same pattern as `addArtworkLayer` etc.: pure `(project, ...) => Project`, no-op on invalid input. Caught and fixed during an independent engineering review — these had initially been hand-edited inline in the `useStudioProject` hook, which both violated the documented dependency direction and triplicated the hex-color validation regex across three files.

## 3D Runtime

- Real WebGL via `@react-three/fiber`/`three`, `frameloop="demand"` (no continuous render loop while idle).
- Camera presets (Front, Back, 3/4 Front today — the manifest declares which presets a garment supports) with orbit/zoom via drei's `OrbitControls`.
- 3-point lighting (key/fill/rim + ambient).
- Isolated error boundary around the canvas only — a WebGL/asset failure never takes down the rest of the Studio.
- Honest async loading state ("Loading garment…") while the manifest/GLB load.
- Resource lifecycle: drei's shared `useGLTF` geometry cache is never mutated or disposed; only per-instance cloned materials are disposed on unmount/manifest change.

## E2E

Six flows, `apps/web/e2e/smoke.spec.ts`:

1. **New 3D project** — choosing the real garment creates a project, renders a real (non-placeholder) WebGL canvas with a plausible bounding box, and unlocks the previously-disabled tools.
2. **Color persistence** — recoloring the garment updates the swatch state; after waiting for the debounced autosave to actually land (not racing it — see Remaining Issues), a reload restores the same color.
3. **Camera** — an orbit drag followed by Back/Front preset clicks keep the canvas visible and update `aria-pressed` correctly.
4. **New/recent project** — a second project appears in recents, switching and deleting both work, and a deleted project stays gone after reload.
5. **Legacy M01 project** — an M01-shaped placeholder `GarmentReference` is seeded directly into IndexedDB; the Studio resolves it to the real garment and surfaces "Matched from an earlier project format."
6. **Mobile** — the garment renders full-viewport at 390×844 with no horizontal overflow, and the bottom tool bar remains reachable and enabled.

One real authoring bug was found and fixed while stabilizing this suite: the canvas's async loading overlay also carries `role="status"`, colliding with the topbar's save-status locator (`page.getByRole('status')`) under strict mode — fixed by scoping the locator to `page.locator('header')`.

## Visual QA

Actually rendered via Playwright + Chromium (Claude-in-Chrome MCP unavailable in this environment, as in M00/M01) at 1440×900, 1280×720, 1024×768, 768×1024, 390×844, 360×800, for the default/black-recolored/back-camera states. **Two real defects found and fixed:**

- A black-recolored garment was nearly invisible against the near-black canvas background — the 3-point rig's rim/fill lights were too weak to separate a low-albedo material from a low-luminance backdrop. Fixed by strengthening the rim light (0.45→1.3) and modestly raising ambient/fill.
- The mobile Inspector `<details>` showed a duplicate "Inspector" heading (the disclosure `<summary>` plus `Inspector`'s own `<h2>`). Fixed with a `showHeading` prop, off for the mobile usage.

Noted, not fixed this pass (see Remaining Issues): the shoulder/sleeve seam gap (asset limitation, documented in `PROVENANCE.md`) and a somewhat small/low-centered default framing on wide desktop canvases — both flagged by an independent design-review pass as acceptable for a development-grade milestone, not blocking.

## Engineering Review

An independent review (`pr-review-toolkit:code-reviewer` subagent) covered R3F/Three lifecycle, disposal, the demand frame loop, camera framing math, trust boundaries, dependency direction, bundle size, and SSR safety. Findings, all real, all fixed and re-verified:

- **Critical:** `setGarmentColor`/`setCameraPreset` hand-edited `Project` fields inline in the `useStudioProject` hook instead of going through `project-engine`, violating CLAUDE.md's own explicit rule and triplicating a hex-color regex across three files. Fixed by adding `packages/project-engine/src/garment.ts`.
- **Real bug:** any canvas resize (including the mobile Inspector `<details>` expanding/collapsing) re-snapped the camera to the active preset, silently discarding the user's orbit. Fixed by splitting `CameraRig`'s single effect into a preset-framing effect (runs only on preset/bounds change) and a resize-only effect (adjusts orbit constraints and re-clamps distance without resetting the angle).
- **Real bug:** `frameGarment`'s own `maxDistance` (`radius * 6`) could be smaller than the aspect-corrected `distance` it returned in the same call, so `OrbitControls.update()` would immediately clamp the camera back in and silently undo the mobile-clipping fix on narrow-enough aspects. Fixed by deriving `maxDistance` from `distance` too; added a regression test sweeping aspects 0.3–3.0.
- **Real bug:** clicking the already-active camera preset did nothing (no way to "reset view" after orbiting), because the preset lookup returns a referentially-stable object. Fixed with a `cameraResetToken` counter, bumped on every `setCameraPreset` call, threaded down to `CameraRig`'s effect dependencies. Verified visually (drag → re-click active preset → view returns to the canonical framing) and via a resize test (drag → resize → orbit preserved).
- **Real defect:** the color swatches and custom-color input were 28px, below this project's own documented 36px touch-target minimum, on exactly the controls that render inside the mobile Inspector sheet. Fixed (28px → 36px).
- **Real gap:** `/studio` statically imported `@threadform/3d-engine`, shipping three.js/drei to the picker/recents screen and any project whose garment can't render. Fixed with `next/dynamic({ssr:false})` — see Performance above.
- **Latent (not yet reachable, fixed anyway):** the color-effect's dependency array didn't include `cloned`, so if a second garment existed today, switching to it while keeping the canvas mounted would have left the color at the new GLB's baked-in default instead of the current selection. Not reachable yet (every garment switch currently unmounts the canvas via the picker), fixed proactively since a second catalog entry is a near-term certainty.
- Everything else audited was verified clean: the manifest trust boundary, `resolveGarmentReference`'s exact-category-only legacy matching, `useResolvedGarment`'s race-free effect, the color round-trip end-to-end, SSR safety (`/studio` prerenders statically with no WebGL calls on the server), and Three.js resource disposal.

Noted but not fixed this pass (below the reporting bar, logged honestly rather than silently dropped): `Project.camera.distance`/`.target`/`.fieldOfViewDegrees` are persisted but currently ignored by the renderer (distance/target are derived from bounds, FOV is hardcoded to 32) — a real inconsistency between stored and rendered state, deferred since fixing it properly means deciding whether user-driven zoom should persist at all, which is a product question beyond this milestone; a `PerspectiveCamera` cast in `CameraRig` that a type-guard would make safer; a manifest's `model.reference` isn't yet restricted to same-origin paths (low risk today — manifests are same-origin static files gated by the catalog).
